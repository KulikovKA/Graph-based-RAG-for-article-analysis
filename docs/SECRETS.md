# Локальные секреты MAIN

Скопируйте `.env.example` в `.env`, а `.env.secrets.example` в `.env.secrets`. Ограничьте доступ к файлам средствами ОС: только владелец и необходимые администраторы; храните резервные копии в защищённом хранилище. Оба файла исключены из Git и Docker context. Не выводите их содержимое в терминал, журналы, историю команд и отчёты. Внешние ключи EPO, OpenAlex и Groq могут оставаться пустыми. Groq не передаётся текущему worker до допуска I-SEC. `STAGE_CACHE_SCOPE_SECRET` — отдельный общий ключ API и worker; он необязателен до подключения кэша, и для новой установки должен быть независимо сгенерирован один раз.

Для существующей установки инвентаризируйте имена в прежних `.env`, `.env.tracking`, окружении процесса, Windows User/Machine и конфигурации контейнеров; сравнивайте значения только в памяти. Окружение процесса является фактическим входом текущего запуска; User/Machine нужно проверить отдельно, так как уже запущенный процесс может их не наследовать. Если источники различаются, выясните реальное использование. Конфигурация контейнера не подтверждает актуальный пароль PostgreSQL, Neo4j или Airflow UI: требуется безопасная проверка аутентификации либо ручное подтверждение. Неподтверждённый конфликт не переносите и не перезаписывайте. Сохраните защищённую копию старых файлов и тома, затем перенесите подтверждённые значения без ротации, разделив несекретные и секретные имена. Не меняйте AUTH_SESSION_SECRET и AIRFLOW_FERNET_KEY. Удалите секреты из старых файлов только после проверки и сохранения защищённой копии. Смена env не меняет учётные данные внутри существующих баз.

Только для первоначальной установки без существующих данных создавайте разные случайные значения: для паролей и webserver key — по 32 байта в hex, для Fernet — URL-safe base64 32 случайных байтов; не используйте стандартные пароли. Пароли, вставляемые в URL, должны состоять из URL-safe символов. Никогда не генерируйте внешние API-ключи. Сгенерированные значения записывайте сразу в защищённый файл без вывода на экран.

Compose запускайте с `--env-file .env --env-file .env.secrets`: второй файл имеет приоритет над первым, а переменные процесса — над обоими. Перед запуском устраните все переменные процесса, используемые в интерполяции Compose, включая `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME`, `COMPOSE_PROFILES`, `COMPOSE_ENV_FILES`, `COMPOSE_DISABLE_ENV_FILE`. Для проверки используйте `docker compose --env-file .env --env-file .env.secrets -f compose.yaml config --quiet`, без вывода развёрнутой конфигурации. Аналогично проверяется `compose.tracking.yaml`. Не включайте DAG при проверке.

Локальный Python не читает Compose env автоматически. Пример с явным выбором имён: `python scripts/run_with_env.py --file .env --file .env.secrets --allow GROQ_API_KEY -- python my_script.py`. Передаются только выбранные имена из файлов; если выбранное имя уже присутствует в процессе, запуск прекращается. Имена не должны повторяться в файлах даже при различии регистра; имена передаются в верхнем регистре. Поддерживается формат `NAME=значение` без кавычек, подстановок, обратных косых черт и встроенных комментариев. Не используйте loader для вывода окружения или запуска непроверенной программы. Он не удаляет другие переменные, уже унаследованные процессом: перед запуском проверьте их состав.

Для разрешённого синтетического live-smoke Groq: `python scripts/run_with_env.py --file .env --file .env.secrets --allow GROQ_API_KEY -- python scripts/smoke_groq_synthetic.py --live`. Запуск требует согласованного бюджета; скрипт ограничивает run четырьмя запросами, 50 000 токенов и 0,02 USD. Используйте исключительно его синтетический ввод. Реальные пользовательские идеи до прохождения I-SEC не отправляются.

## План переноса существующей установки

1. До изменения файлов подтвердите действующие учётные данные аутентифицированным чтением. В текущем аудите пароль Neo4j из конфигурации контейнера подтвердился по Bolt, а значение прежнего `.env` — нет; кандидат контейнера можно использовать после повторного подтверждения непосредственно перед переносом. Пароль PostgreSQL приложения из `.env` не подтвердился: прежний кандидат допускается перенести в защищённый файл без изменения, отметив его неподтверждённым. Полная приёмка остаётся заблокированной до выяснения действующего значения. Повторите проверку учётных данных после любого изменения среды.
2. Подготовьте защищённое место для отката: шифрованное хранилище или каталог с Windows ACL только для владельца и необходимых администраторов. Проверьте применённые права до записи резервной копии исходных файлов. Не создавайте промежуточные копии в общедоступных или временных каталогах; не записывайте секреты в историю команд, журнал или аргументы процесса.
3. В памяти разделите исходные значения по именам шаблонов, перенесите подтверждённые значения, включая Neo4j, и сохраните AUTH и Fernet без изменения. Неподтверждённый кандидат PostgreSQL переносите побайтно без изменения и явно фиксируйте его статус; аутентификацию нельзя считать пройденной. Новые внешние ключи оставьте пустыми, если их нет. Отдельный новый ключ области кэша создаётся однократно при первоначальной настройке кэша. Проверяйте повторы имён без учёта регистра и конфликтующие переменные процесса.
4. Создайте кандидаты новых файлов только внутри защищённого каталога с проверенным ACL, сравните значения и имена в памяти, проверьте `config --quiet` без запуска служб. Затем замените файлы согласованной операцией с возможностью восстановления защищённых копий. Не запускайте tracking provision, не пересоздавайте контейнеры и не включайте DAG при проверке переноса.
5. Проверяйте аутентифицированные read-only запросы и доступ клиентов. При ошибке восстановите исходные файлы из защищённой копии, не меняя данные и тома; при необходимости верните предыдущую конфигурацию доступа. Резервную копию сохраняйте в том же защищённом хранилище по политике владельца.

Если действующий пароль PostgreSQL приложения не найден, сохраните прежний `POSTGRES_PASSWORD` в `.env.secrets` побайтно и удалите его из `.env`; такой перенос не подтверждает работоспособность подключения. Не объявляйте миграцию полностью принятой, не пересоздавайте приложение и не запускайте миграции БД. Для завершения найдите действующий пароль в защищённых источниках владельца и подтвердите его read-only подключением к тому же экземпляру; смена пароля, reset роли и provision не входят в эту процедуру.

## Отдельная ротация и откат

Ротация — отдельная операция, не часть переноса. Сначала определите затронутые сервисы и потребителей, сохраните проверяемые резервные копии данных, ролей и исходных секретов, согласуйте окно и порядок изменения пароля в сервисе, файле и всех клиентах. Проверяйте вход и доступ к прежним данным без вывода значений. При сбое восстановите согласованные предыдущие значения и конфигурацию сервиса, проверьте аутентификацию и чтение; не удаляйте тома. Fernet защищает сохранённые данные Airflow: замену выполняйте только по штатной процедуре с сохранением старого ключа до завершения перекодирования и проверкой восстановления. Ключ AUTH и сессии требуют отдельного плана совместимости; изменение ключей данных без этого плана недопустимо.

- PostgreSQL приложения, Airflow и MLflow: отдельно смените пароль соответствующей роли в БД, защищённом файле и клиентах в согласованное окно; проверьте аутентифицированное чтение каждой ролью. При неудаче восстановите прежний пароль роли и потребителей. Provision tracking меняет runtime-роль и не является проверкой.
- Neo4j: смените пароль существующего пользователя штатной процедурой БД и синхронизируйте клиентов; проверьте Bolt-аутентификацию и read-only запрос. Верните прежний пароль в БД и клиентах при сбое; `NEO4J_AUTH` сам по себе не меняет пароль на существующем томе.
- Redis: согласованно обновите конфигурацию службы и URL клиентов, затем проверьте аутентифицированный ping и доступ потребителей. При сбое верните прежнюю конфигурацию и URL. Пароль передаётся в конфигурацию Redis через stdin, а не в командной строке; управляющие символы отклоняются.
- Airflow UI: измените пароль существующей учётной записи штатным администрированием Airflow и защищённый файл, проверьте вход, затем при необходимости верните старый пароль штатным способом. Перезапуск init не подтверждает изменение существующей записи.
- Ключи внешних API: создайте замену у провайдера, обновите только необходимых потребителей и проверьте ограниченный разрешённый запрос; старый ключ отзывайте после проверки. При сбое верните старый ключ, пока он действителен. Groq с реальными идеями остаётся за I-SEC.
- `STAGE_CACHE_SCOPE_SECRET`: согласуйте сброс или устаревание кэша, одновременно обновите API и worker, затем проверьте изоляцию и промахи кэша. Откат требует прежнего ключа на обоих потребителях и совместимых записей кэша.
