# INT-GROQ-001 — адаптер Groq

Опоры: [LLM_CONTRACTS](../LLM_CONTRACTS.md), [SECURITY](../SECURITY.md), ADR-011/014 и карточка INT-GROQ-001. Этот этап реализует серверный адаптер `InferenceProvider`, конфигурацию и проверки mock HTTP. Действующие Planner, Analyst, DB/SSE lifecycle, локальные embeddings и reranker сохраняют контракты. Замена рабочего профиля, выставление квот проекта и пользовательский трафик входят в интеграцию.

Конфигурация привязывает роль (Planner, Agent, Analyst, Relation Classifier, Narrative, Extractor, Judge) к model ID, prompt version, capability, timeout и пределу output. Секрет поступает из защищённой среды. Адаптер принимает доменный JSON Schema, обрабатывает выдачу в `JsonResult`, возвращает в текстовом интерфейсе только финальный контент и делегирует embed/rerank локальному порту. Доменные валидаторы вызывающей стороны остаются обязательными. Разрешается настроенный JSON-schema best effort или strict для совместимой схемы. Профиль без подтверждённой capability отклоняется локально. [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs)

Deadline и cancellation охватывают очередь, сеть и backoff. Общий объект бюджета имеет scope одного анализа, учитывает все отправки, в том числе retries и отдельные вызовы ролей. Резерв запросов, токенов и оценочной стоимости проверяется до сети. Для неизвестного usage сохраняется причина, резерв за неподтверждённую попытку не возвращается. Оценка цены вычисляется по конфигурации тарифов с отметкой валюты и источника. Адаптер ограничивает параллелизм и размер ответа. Ошибки типизированы, credentials, запросы, необработанные provider payloads и reasoning в ошибках/метриках отсутствуют.

| --- | --- | --- |
| GROQ-1 | Заданы роли и capabilities → на JSON/текстовую роль приходит допустимый запрос → правильная модель, режим, лимиты и неизменный доменный результат | Mock HTTP, проверка тела и `JsonResult`; существующие тесты inference |
| GROQ-2 | Пустой, некорректный или не соответствующий schema ответ, либо отсутствует capability → вызов завершается типизированной безопасной ошибкой → сырые данные и reasoning не раскрываются | Mock HTTP, negative schema/canary |
| GROQ-3 | 429, временный HTTP 5xx или transport error → повтор ограничен общим deadline/budget и валидным Retry-After → 401/403/400 и ошибки схемы не повторяются | Mock HTTP с управляемой задержкой |
| GROQ-4 | Отмена во время HTTP/backoff, deadline или поздний ответ → вызов завершён безопасно → новое поколение результата не публикуется; consumed budget не возвращается без подтверждения | Mock transport, race/timeout и существующие тесты lease fencing |
| GROQ-5 | Несколько ролей/retries и неполный usage → общий бюджет ограничивает запросы, токены и стоимость → известное usage и версия тарифа отделимы от неизвестных значений | Mock HTTP, проверка бюджета и metadata |

### Изолированная синтетическая проверка классификации и narrative

Синтетический `relation_classifier` использует действующие `RELATION_LABELS` и `RUBRIC`, принимает только фиксированную тестовую пару и выдаёт типизированную метку из разрешённого списка. Вероятности и confidence отсутствуют: генерация числа не подтверждает калибровку. При неверной метке или лишнем поле результат отклоняется типизированной ошибкой без сырого ответа. Эта форма не является заменой `RelationDecision` и не подключается к worker или SystemOne.

Для синтетического narrative задан отдельный профиль `narrative_synthetic_v1`; действующий Analyst продолжает использовать `analyst_v4`. Четыре сценария — Planner, Analyst, Narrative и Relation Classifier — выполняются с общим бюджетом: не более четырёх запросов, 50 000 зарезервированных токенов и 0,02 USD расчётного резерва, без retries. По умолчанию используется mock HTTP; явный `--live` требует ключ из среды процесса и предварительного согласования лимита. Проверить каждый профиль, доменную валидацию, запрет некорректной метки/лишних полей и общий лимит компонентными тестами; mock не подтверждает качество или доступность реальной модели.

Подключение реального классификатора требует выбора модели, калибровки и сравнения с действующим SystemOne, согласованного контракта результата, разрешённого smoke и I-SEC. До их выполнения пользовательский runtime и существующий классификатор не меняются. Кандидат `openai/gpt-oss-20b`, schema capability и пример тарифа проверяются по [моделям Groq](https://console.groq.com/docs/models) и [Structured Outputs](https://console.groq.com/docs/structured-outputs); повторная проверка обязательна перед сетевым использованием.

Компонентная реализация в `src/app/integrations/`, аддитивные поля в `src/app/domain/inference.py` и изолированный профиль в `config/`. Рабочее подключение worker и роль Judge проверяются на I-SEC/I-AGENT/I-EVAL/I-OBS. Разрешённый smoke каждой роли и целевой запуск без локальной генерации нужны для полной приёмки. Временный откат использует работающую сейчас конфигурацию и неизменённые lifecycle/DTO. Данные пользователя разрешено отправлять только после I-SEC.
