# APP-AIR-001 — инкремент Airflow

Опоры: [ARCHITECTURE](../ARCHITECTURE.md), [DATA_MODEL](../DATA_MODEL.md), ADR-002/015, INT-KG и I-CORPUS. DAG вызывает переиспользуемые source adapters, ingestion, extraction/indexing и существующие outbox/ACK в офлайн-контуре. Первая волна работает через внедряемые порты на fixtures. Расписание/Compose, реальные подключения, урегулирование квот и публикация на готовом корпусе относятся к I-AIR.

Вход — interval с UTC bounds, разрешённые EPO/OpenAlex scope/config и последнее durable состояние. Discovery выдаёт страницу source IDs/revisions и позицию страницы или watermark. Нормализация/ingestion использует source/external ID/content hash. Неизменные ревизии не требуют повторной проекции. Идемпотентная заявка сохраняет revision и отправляет отдельные задания KG и vector. Завершение страницы/интервала и переключение поколения разрешены только после QA и обоих подтверждений для изменённых ревизий. При частичном сбое повтор восстанавливается по durable checkpoint/outbox; предыдущая опубликованная версия остаётся читаемой.

Настройки подключений получаются через механизм секретов/Connections Airflow либо текущие защищённые env adapters. Payload логов и XCom ограничен stage, статусом, счётчиками и неприватными идентификаторами. Произвольные источники/URL и пользовательские данные не входят в DAG inputs. Пределы на интервалы, страницы, запросы и retries задаются конфигурацией. Повтор использует тот же стабильный набор IDs и revision keys.

| ID | Given → When → Then | Проверка |
| --- | --- | --- |
| AIR-1 | EPO/OpenAlex fixtures дают новые, повторные и изменённые документы → bounded discovery/ingestion → обработаны только новые/изменённые ревизии, пустая страница завершает цикл | Fixture source и реестр вызовов |
| AIR-2 | Изменённая ревизия → ingestion/chunks/extraction → прежними портами ставятся обе проекции с pinned revision/provenance | Test doubles projectors и фикстуры ingestion |
| AIR-3 | Векторный или KG ACK отсутствует → DAG повторяет нужную работу → publish/checkpoint наступает после обоих ACK/QA и повтор интервала идемпотентен | Failure injection и replay |
| AIR-4 | Неразрешённый source, невалидный документ, квота или сбой зависимости → safe failure, bounded retry, checkpoint не обгоняет данные → секреты и raw payload не публикуются | Negative fixture/log/canary |
| AIR-5 | Запущен DAG на разрешённом замороженном снимке → инкремент виден в обоих online indexes после publish → прежняя версия читается в случае partial projection | Live I-AIR после I-CORPUS, без полного backfill |

Файлы первой волны — `airflow/` (DAG и bridge), fixtures и targeted tests. Общий `compose.yaml`, online worker и публикацию поколения в рабочей инфраструктуре соединяет оркестратор на I-AIR. Откат останавливает расписание; durable outbox и текущее поколение доступны для возобновления.

## Контракт планировщика и эксплуатационная проверка

MAIN развёртывает Airflow 2.11.0 с LocalExecutor, scheduler, webserver и выделенной PostgreSQL. Единственный DAG при создании paused. Run становится допустимым после ручного включения и наступления очередной календарной границы. CronTriggerTimetable с явным интервалом 24 часа, зоной Europe/Moscow и конфигурируемым ежедневным cron (по умолчанию 0 3 * * *) задаёт окно [конец − 24 часа, конец). Смена часов запуска требует сверки перекрытий с последним checkpoint. Включение после простоя пропускает старые границы, catchup выключен, одновременно допускается один run. Manual trigger использует переданный timetable момент и предыдущие 24 часа, произвольный conf игнорируется. Ручной запуск требует решения оператора.

AIR-6. При первом старте scheduler зарегистрированный DAG paused, список runs пуст. При проверке timetable в изоляции следующие сутки заканчиваются в 03:00 Москвы (00:00 UTC). Время старта worker фиксируется отдельно от logical_date и границ окна. UI по умолчанию показывает Москву, индивидуальный выбор браузера проверяется по индикатору зоны. Время ОС не участвует в расчёте.

AIR-7. Сбой порта даёт безопасный FAILED и сохраняет checkpoint. Сбой tracking сохраняет безопасное событие локально и не влияет на результат DAG. Публикация только после AIR-3. Откат — пауза целевого DAG, остановка сервисов с сохранением томов. Реальные источники закрыты до I-CORPUS/I-AIR.

Airflow хранит уже рассчитанный next_dagrun в metadata DB. Для такой записи при задержке до следующей календарной границы окно ещё актуально. Если прошла следующая граница, задача получает SKIPPED до обращения к портам. В UI Next Run показывает logical_date (начало окна), поле next_dagrun_create_after задаёт время допуска. Переключение существующего DAG на реальных сервисах проверяется отдельно в I-AIR.

## Контракт подключения постоянного состояния

`configured_ports()` остаётся отключённой точкой подключения. Перед I-AIR требуется постоянное состояние по `(source, interval_start_utc, interval_end_utc)`, сохранённые страницы и версия конфигурации обработки. Разрешено возобновление после повторного старта процесса. При неопределённом результате commit повтор того же frozen page идентифицируется по source/window/cursor и точному набору revision keys, возвращает успех без новой публикации. Если входы изменились, порт прекращает обработку старой записи. При конкурентном запуске publish проверяет ожидаемый checkpoint и версии ACK обеих проекций. QA, активация поколения и обновление checkpoint согласуются в транзакции PostgreSQL, а внешние операции повторяются по стабильным ID.

Текущий `IngestionService.acknowledge` публикует поколение после двух ACK отдельной ревизии. Для DAG его публикацию надо отложить до проверки QA и commit страницы. Прямое подключение этого метода к `project` нарушило бы AIR-3. На временном снимке I-CORPUS нужно проверить несовпавшие версии ACK, отказ QA, сбой после каждого ACK и потерю ответа после commit, после чего повторно прочитать как новое, так и предыдущее поколение.

| ID | Дано → действие → результат | Проверка |
| --- | --- | --- |
| AIR-8 | Замороженная страница и один ACK сохранены → процесс checkpoint создан заново → восстановлены зафиксированный набор ревизий и результат повторной записи | Постоянный тестовый backend, отдельные подключения |
| AIR-9 | Есть QA, оспоренный checkpoint или несовпадающие ACK → попытка commit → активный указатель и checkpoint меняются одной транзакцией только при совпадении всех предпосылок; повтор успешного commit идемпотентен | Тест изолированной портовой реализации, I-AIR для настоящих projectors |

В прототипе постоянного состояния подготовленная страница закрепляет полный набор discovery, подмножество изменённых ревизий и их целевое поколение. QA и оба ACK привязаны к той же ревизии и целевому поколению с версиями проекторов. Пустая или неизменённая страница продвигает checkpoint без смены активного поколения. PostgreSQL-тесты используют отдельную схему и синтетические подтверждения. Для подключения `configured_ports()` требуется проверенный манифест членства и адаптеры реальных источников, QA и проекторов на I-CORPUS/I-AIR.
