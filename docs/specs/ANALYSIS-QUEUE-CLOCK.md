# Аналитическая очередь — единый источник времени

Основание — нестабильные захваты jobs в [SDD_VERIFICATION_REPORT](../SDD_VERIFICATION_REPORT.md). PostgreSQL задаёт `next_attempt_at` при постановке, прежний worker сравнивал это значение со временем Windows. Аналитическая очередь использует время PostgreSQL для отбора, lease, heartbeat, повторов, отмены и terminal timestamps. После получения блокировок решение об аренде использует время нового SQL statement, включая операции в длительной транзакции. Временные поля хранятся как `timestamptz`. Локальный monotonic clock продолжает ограничивать ожидания и сетевые дедлайны.

| ID | Given → When → Then | Проверка |
|---|---|---|
| CLOCK-1 | Время worker опережает или отстаёт на часы → claim/heartbeat → новая job доступна, lease и heartbeat согласованы с UTC PostgreSQL | PostgreSQL, подстановка времени приложения |
| CLOCK-2 | Lease истёк, в том числе внутри уже открытой транзакции → попытка записи/heartbeat → отказ, новый токен захвата блокирует старого worker | PostgreSQL, управляемый expiry и проверка старого токена |
| CLOCK-3 | Job отложена или запрошена отмена → следующий claim и завершение → delay соблюдается, результат отменённого worker отвергается, terminal time берётся из БД | PostgreSQL, retry/cancel/fencing |

Граница изменений — `storage/jobs.py`, регрессии аналитической очереди. Миграция схемы не требуется. Сохранённые сроки истекают по существующим значениям. Airflow timetable и внешний inference имеют собственные контракты времени.
